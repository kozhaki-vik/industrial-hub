# Правила проекта: Industrial Hub

## Core Styling & Theming
* В приложении две темы: Light (по умолчанию) и Dark.
* **Light mode:** Использует чистый, дорогой инженерный стиль интерфейса. Фон — `#F8F9FA` (`bg-[#F8F9FA]`), карточки — `bg-white`, текст — `slate-900` / `slate-500`.
* **Dark mode:** Использует глубокие темные тона. Карточки — `bg-slate-900`, текст — `slate-100` / `slate-400`.
* **Accent color:** Акцентный цвет для обеих тем — Industrial Orange (`orange-500`).
* Всегда использовать Tailwind CSS class-based dark mode (например, `dark:bg-slate-900`).
* Кнопки управления должны иметь четкую контрастную обводку (`border-slate-200 dark:border-slate-700`), читаемый фон и скругления `rounded-xl` / `rounded-lg`.

## Internationalization (i18n)
* Приложение поддерживает 3 языка: Русский (`ru`), Английский (`en`) и Украинский (`ua`).
* Русский язык является языком по умолчанию.
* Убедиться, что украинский ВСЕГДА сокращается как `ua`, а не `uk`.
* Все пользовательские строки (имена, описания, ошибки, подсказки) должны управляться через `react-i18next` и храниться в `src/i18n.js`.
* В Discord-боте (`Discord_Hub`) также соблюдается строгая локализация на `ru`, `en`, `ua` через `src/utils/i18n.js` со слэш-командами (`setNameLocalizations`, `setDescriptionLocalizations`).

## Система автообновления (Auto-update System)
* **Репозитории:** Для безопасности используются ДВА репозитория: `kozhaki-vik/industrial-hub` (Приватный, только для кода) и `kozhaki-vik/industrial-hub-releases` (Публичный, только для скомпилированных обновлений).
* **Хранение сборок:** В формате одного `.exe` файла осуществляется в релизах GitHub (GitHub Releases) в публичном репозитории `kozhaki-vik/industrial-hub-releases`.
* **Ветви версий:** В приложении есть переключатель "Main / Test" сборок. Переключение на "Test" защищено ПИН-кодом `2136` (зашит в клиенте). 
  * `Test`-версии — это релизы на GitHub с пометкой `Pre-release`.
  * `Main`-версии — обычные стабильные релизы (`Release`).
* **Webhooks:** Сервер получает уведомление о новой версии через GitHub Webhooks (из репозитория релизов) и мгновенно оповещает все подключенные клиенты.
* **ВНИМАНИЕ (Кэш GitHub API):** При получении вебхука клиент ОБЯЗАН использовать Cache-Buster (добавлять `?t=${Date.now()}` к ссылке) при запросе к GitHub API (`/releases`). Иначе из-за кэширования CDN Fastly (на 60 секунд) программа скачает старую версию!
* **ВНИМАНИЕ (Скрипт загрузки):** Скрипт публикации `upload_release.ps1` всегда должен создавать релиз со статусом черновика (`draft: $true`), загружать 100-мегабайтный `.exe` файл, и только после полной загрузки менять статус на `draft: $false`. Это гарантирует, что вебхук сработает только тогда, когда файл реально доступен.
* **Логика скачивания:** Клиенты скачивают файл обновления (готовый `.exe`) напрямую с публичного GitHub в новую папку, название которой соответствует номеру версии (например, `app-1.2.0`), рядом со старой версией. После скачивания старая версия запускает новый `.exe` (передавая `--cleanup-dir`). Запущенная новая версия должна принудительно закрыть процесс старой версии и полностью удалить её папку.
* **Архитектура Portable:** Приложение компилируется с `target: portable`. `process.execPath` внутри приложения указывает на временную папку в `%TEMP%`.
* **ВНИМАНИЕ:** Для получения реального пути к исходному `.exe` файлу, необходимо всегда использовать `process.env.PORTABLE_EXECUTABLE_DIR` (как это реализовано в хелпере `getRealAppPath()` в `main.js`). Иначе скачается во временную папку и удалится при перезагрузке!

## Версионирование (Versioning)
* Формат состоит из 3 чисел (например, `2.2.54`):
  * **Первое число (2):** Глобальная версия (Major).
  * **Второе число (2):** Версия Main ветки. Увеличивается только при явном указании сделать Main релиз.
  * **Третье число (54):** Версия Test ветки. Увеличивается на +1 при каждом изменении.
* **ВАЖНО:** После любых изменений агент обязан увеличивать третью цифру версии (тестовую) на `+1` в `package.json`. Выпуск Main-сборки делается только по прямому приказу.

## Сборка и публикация обновлений (Build & Release)
* Клиент (Electron) компилируется в формат одного исполняемого файла (Standalone/Portable `.exe`).
* **Git:** ИИ ОБЯЗАН делать коммит изменений (`git commit -am "message"`) и отправлять их в приватный репозиторий (`git push`) перед или сразу после создания новой версии.
* **Сборка:** Выполнить `npm run build`, а затем `npx electron-builder --win`.
* **Публикация:** После успешной сборки, ИИ обязан самостоятельно загрузить `.exe` файл из папки `release/` в GitHub Releases, используя скрипт:
  `.\upload_release.ps1 -Version "X.X.X" -FilePath "release\Industrial Hub X.X.X.exe" -IsPreRelease $true`
* Сервер больше не занимается хранением/раздачей обновлений (архивы `client.zip` больше не используются).

## Цифровая подпись (Code Signing)
* **ВАЖНО:** Все скомпилированные `.exe` файлы (например, `Launcher.exe`) необходимо обязательно подписывать цифровым сертификатом из хранилища пользователя (`Thumbprint: CF5FD177247FC2EEB561B69BE223EF0757218C08`).
* **Утилита:** `C:\Users\Developer\AppData\Local\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0\windows-10\x64\signtool.exe`
* **Пример команды:** `signtool.exe sign /sha1 CF5FD177247FC2EEB561B69BE223EF0757218C08 /fd sha256 /tr http://timestamp.digicert.com /td sha256 Launcher.exe`
* *(В скрипте `build_launcher.bat` подпись уже интегрирована)*. При создании любых новых исполняемых файлов ИИ обязан убедиться, что они подписаны.

## Node.js & Зависимости (Backend)
* Серверная часть и бот используют CommonJS (`require`).
* **СТРОГИЙ ЗАПРЕТ:** Запрещено импортировать npm-пакеты, которые поставляются исключительно как ES Modules (например, новые версии `uuid`, `node-fetch`). При попытке запуска это приведет к фатальному крашу `ERR_REQUIRE_ESM`.
* Вместо пакета `uuid` всегда использовать встроенную стандартную функцию `crypto.randomUUID()`.

## WebSockets & Состояние гонки (Race Condition)
* При подключении к WebSocket на клиенте статус `online` (в `NetworkContext`) должен устанавливаться **исключительно после** получения от сервера подтверждения авторизации (событие `auth_success`), а не сразу в событии `ws.onopen`.
* Это гарантирует, что к моменту, когда React-компоненты начинают слать запросы, сервер уже знает HWID клиента и не возвращает ошибку базы данных `SQLITE_MISUSE`.
* **Стабильность WebSocket и Heartbeat:** Все постоянные соединения (десктопный клиент и Discord-бот) обязаны отправлять регулярные heartbeat-пакеты (клиент — раз в 60 секунд, бот — раз в 25 секунд). Это предотвращает разрыв соединения прокси-сервером Nginx по таймауту неактивности (`proxy_read_timeout 120s`).
* **Server-Side Rate Limiting:** Сервер (`ws/clan.js`) защищен троттлингом (не более 5 прокси-запросов в секунду на 1 HWID), отсекая спам до обращения к Discord API (`429 Too Many Requests`).

## Архитектура и безопасность Discord-бота (Discord_Hub)
* **СТРОГИЙ ЗАПРЕТ БЭКДОРОВ:** Категорически запрещено создавать скрытые административные команды (вроде `!admin`), жестко зашитые ID суперпользователей (`SUPER_ADMIN_ID`) или автоматическую выдачу ролей с правами `Administrator`. Управление ботом осуществляется строго через настроенные роли клана (Лидер, Заместитель, Коллер).
* **Защита от крашей в ЛС (DM Safety):** Все события взаимодействия (`interactionCreate.js`, `messageCreate.js`) обязаны проверять наличие гильдии `if (!interaction.guild)`.
* **Нативные Discord Modals:** Подача заявок в клан осуществляется через всплывающие модальные окна Discord (`ModalBuilder`) с полями: возраст, часы в Rust, ссылка на Steam / SteamID64, опыт игры.
* **HTML-транскрипты тикетов в стиле Discord Dark:** При закрытии тикета бот генерирует полноценный интерактивный `.html` файл с дизайном Discord (темная тема, аватары, markdown, эмбеды, карточки файлов). Файл отправляется в специальный канал транскриптов и в канал аудита логов (строго без отправки в ЛС заявителю).
* **Мульти-аккаунты Steam кандидата:** Регулярное выражение `/(7656119\d{10})/g` извлекает все указанные кандидатом Steam-аккаунты. Бот суммирует проверенные часы со всех профилей (`10000 ч. (Steam: 9000 ч. (5000 + 1000 + 3000))`) и проверяет баны по каждому из них.
* **Проверка часов в Rust:** Проверка минимального порога (`minHours`) выполняется СТРОГО по анкете, не наказывая кандидатов со скрытым профилем Steam (если строгая проверка профиля выключена).
* **Аудит скрытых отказов (Silent Auto-Reject):** При включенном `silentAutoReject = true` (когда канал тикета не создается) бот ОБЯЗАН отправить полную карточку кандидата (все аккаунты Steam, Battlemetrics, опыт `exp`, аватар и подробную причину отказа) в канал авто-отклонений / аудит логов.
* **Система предупреждений (Clan Warnings System):**
  - Модель `UserWarning` в PostgreSQL (Prisma). Сервис `warnService.js` управляет жизненным циклом варнов (выдача, снятие конкретного, полная очистка, аудит, отправка ЛС).
  - При выдаче предупреждения ОБЯЗАТЕЛЬНО фиксируются `moderatorId` и `moderatorTag` выдавшего (пользователь клиента или Discord модератор), обеспечивая прозрачный аудит истории.
  - Настраиваемый порог предупреждений (3, 4 или 5) с автоматическим применением санкций: Таймаут (1 час, 1 день, 1 неделя), Кик или Бан.
  - В приложении: колонка со статусом предупреждений в «Статистике» (`⚠️ N/3` / `✓ 0`), клик открывает интерактивное модальное окно `UserWarningsModal`. Во вкладке «Модерация» — настройки системы и общая таблица предупреждений клана.
* **Автоматическая защита от модерации (Moderation Exemption):**
  - Автоматически от правил модерации (`Anti-Mention`, `Bad Words Blacklist`) освобождаются **только** роли Лидера (`leaderRoleId`) и Заместителя (`deputyLeaderRoleId`).
  - Роль Коллера (`callerRoleId`) по умолчанию **НЕ** защищена от модерации автоматически. При необходимости администратор может вручную добавить роль Коллера в список исключений (белый список).
* **Клановые роли и терминология:**
  - Роль Коллера строго именуется: `Coller` / `Коллер` (внутренний ключ `callerRoleId` сохранен для обратной совместимости).
  - Фармер ресурсов: `Фармер (Ресурсы)` / `Miner / Farmer (Resources)` (`farmerRoleId`).
  - Фермер урожая/растений: `Фермер (Урожай)` / `Farmer (Crops / Plants)` (`plantFarmerRoleId`).
  - Спонсор: `Спонсор` / `Sponsor` (`sponsorRoleId`).
* **Anti-Raid детекция:** Бот отслеживает всплески входов (5+ за 10 секунд) и маркирует свежесозданные аккаунты (< 3 дней) предупреждениями в аудит-логе.
* **Промышленная база данных PostgreSQL:** Бот работает на СУБД PostgreSQL (`schema.prisma` с `provider = "postgresql"` и `url = env("DATABASE_URL")`).

## Эргономика и компоненты Клан Менеджера
* **Карточки ролей (Role Cards Layout):** В карточках ролей (стандартных и кастомных) не должно быть верхних избыточных заголовков-меток (`● LEADER`, `● DEPUTY` и т.д.). Бейдж статуса привязки (`✓ Привязано` / `Не привязано`) и кнопка удаления шаблона роли (`🗑️`) располагаются в нижней строке (footer) карточки.
* **Универсальные переключатели (ToggleSwitch):** Вместо стандартных чекбоксов для опций включения/выключения повсеместно используется интерактивный ползунок с явной индикацией `Вкл` / `Выкл` (`On` / `Off`, `Увімк` / `Вимк`).
* **Зафиксированный сайдбар:** Сайдбар с разделами зафиксирован (`w-64`, без собственной прокрутки, шрифт `text-sm font-medium`, иконки `w-4 h-4`). Прокручивается исключительно внутренняя область содержимого выбранной вкладки (`overflow-y-auto`).
* **Фоновое автосохранение:** Нижние панели ручного сохранения отсутствуют — все данные сохраняются на лету с дебаунсом и батчингом, а статус синхронизации компактно отображается в шапке сайдбара.

## Валидация форм (Universal Form Validation)
* При отправке, сохранении или применении любых форм по всей программе ОБЯЗАТЕЛЬНО вызывать `validateForm()` из `src/utils/formValidation.js`.
* Все обязательные поля помечаются `required` или `data-required="true"`.
* При наличии ошибок система автоматически плавно скроллит страницу или модальное окно к **первому незаполненному полю сверху вниз**, устанавливает на него фокус, включает красную рамку `.input-error-highlight` и анимацию встряхивания `.animate-field-shake`.
* На все формы обязательно устанавливать атрибут `noValidate` для предотвращения блокировки стандартными тултипами браузера.
