# Правила проекта: Industrial Hub

## Core Styling & Theming
* В приложении две темы: Light (по умолчанию) и Dark.
* **Light mode:** Использует чистый, дорогой инженерный стиль интерфейса. Фон — `#F8F9FA` (`bg-[#F8F9FA]`), карточки — `bg-white`, текст — `slate-900` / `slate-500`.
* **Dark mode:** Использует глубокие темные тона. Карточки — `bg-slate-900`, текст — `slate-100` / `slate-400`.
* **Accent color:** Акцентный цвет для обеих тем — Industrial Orange (`orange-500`).
* Всегда использовать Tailwind CSS class-based dark mode (например, `dark:bg-slate-900`).

## Internationalization (i18n)
* Приложение поддерживает 3 языка: Русский (`ru`), Английский (`en`) и Украинский (`ua`).
* Русский язык является языком по умолчанию.
* Убедиться, что украинский ВСЕГДА сокращается как `ua`, а не `uk`.
* Все пользовательские строки (имена, описания, ошибки, подсказки) должны управляться через `react-i18next` и храниться в `src/i18n.js`.

## Система автообновления (Auto-update System)
* **Репозитории:** Для безопасности используются ДВА репозитория: `kozhaki-vik/industrial-hub` (Приватный, только для кода) и `kozhaki-vik/industrial-hub-releases` (Публичный, только для скомпилированных обновлений).
* **Хранение сборок:** В формате одного `.exe` файла осуществляется в релизах GitHub (GitHub Releases) в публичном репозитории `kozhaki-vik/industrial-hub-releases`.
* **Ветви версий:** В приложении есть переключатель "Main / Test" сборок. Переключение на "Test" защищено ПИН-кодом `2136` (зашит в клиенте). 
  * `Test`-версии — это релизы на GitHub с пометкой `Pre-release`.
  * `Main`-версии — обычные стабильные релизы (`Release`).
* **Webhooks:** Сервер получает уведомление о новой версии через GitHub Webhooks (из репозитория релизов) и мгновенно оповещает все подключенные клиенты.
* **ВНИМАНИЕ (Кэш GitHub API):** При получении вебхука клиент ОБЯЗАН использовать Cache-Buster (добавлять `?t=${Date.now()}` к ссылке) при запросе к GitHub API (`/releases`). Иначе из-за кэширования CDN Fastly (на 60 секунд) программа скачает старую версию!
* **ВНИМАНИЕ (Скрипт загрузки):** Скрипт публикации `upload_release.ps1` всегда должен создавать релиз со статусом черновика (`draft: $true`), загружать 100-мегабайтный `.exe` файл, и только после полной загрузки менять статус на `draft: $false`. Это гарантирует, что вебхук сработает только тогда, когда файл реально доступен.
* **Логика скачивания:** Клиенты скачивают файл обновления (готовый `.exe`) напрямую с публичного GitHub в новую папку, название которой соответствует номеру версии (например, `app-1.2.0`), рядом со старой версией. После скачивания старая версия запускает новый `.exe` (передавая `--cleanup-dir`). Запущенная новая версия должна принудительно закрыть процесс старой версии и полностью удалить её папку.
* **Архитектура Portable:** Приложение компилируется с `target: portable`. `process.execPath` внутри приложения указывает на временную папку в `%TEMP%`.
* **ВНИМАНИЕ:** Для получения реального пути к исходному `.exe` файлу, необходимо всегда использовать `process.env.PORTABLE_EXECUTABLE_DIR` (как это реализовано в хелпере `getRealAppPath()` в `main.js`). Иначе скачается во временную папку и удалится при перезагрузке!

## Версионирование (Versioning)
* Формат состоит из 3 чисел (например, `2.2.54`):
  * **Первое число (2):** Глобальная версия (Major).
  * **Второе число (2):** Версия Main ветки. Увеличивается только при явном указании сделать Main релиз.
  * **Третье число (54):** Версия Test ветки. Увеличивается на +1 при каждом изменении.
* **ВАЖНО:** После любых изменений агент обязан увеличивать третью цифру версии (тестовую) на `+1` в `package.json`. Выпуск Main-сборки делается только по прямому приказу.

## Сборка и публикация обновлений (Build & Release)
* Клиент (Electron) компилируется в формат одного исполняемого файла (Standalone/Portable `.exe`).
* **Git:** ИИ ОБЯЗАН делать коммит изменений (`git commit -am "message"`) и отправлять их в приватный репозиторий (`git push`) перед или сразу после создания новой версии.
* **Сборка:** Выполнить `npm run build`, а затем `npx electron-builder --win`.
* **Публикация:** После успешной сборки, ИИ обязан самостоятельно загрузить `.exe` файл из папки `release/` в GitHub Releases, используя скрипт:
  `.\upload_release.ps1 -Version "X.X.X" -FilePath "release\Industrial Hub X.X.X.exe" -IsPreRelease $true`
* Сервер больше не занимается хранением/раздачей обновлений (архивы `client.zip` больше не используются).

## Цифровая подпись (Code Signing)
* **ВАЖНО:** Все скомпилированные `.exe` файлы (например, `Launcher.exe`) необходимо обязательно подписывать цифровым сертификатом из хранилища пользователя (`Thumbprint: CF5FD177247FC2EEB561B69BE223EF0757218C08`).
* **Утилита:** `C:\Users\Developer\AppData\Local\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0\windows-10\x64\signtool.exe`
* **Пример команды:** `signtool.exe sign /sha1 CF5FD177247FC2EEB561B69BE223EF0757218C08 /fd sha256 /tr http://timestamp.digicert.com /td sha256 Launcher.exe`
* *(В скрипте `build_launcher.bat` подпись уже интегрирована)*. При создании любых новых исполняемых файлов ИИ обязан убедиться, что они подписаны.

## Логика проверок целостности (Integrity Checks)
* **Проверка Rust:** Ограничена сканированием ровно двух конфигурационных файлов: `\cfg\keys.cfg` и `\cfg\client.cfg`.
* **Проверка программы (App Integrity):** Ограничена сканированием 10 ключевых файлов (например, скомпилированный `app.asar`, `package.json`, исполняемый `.exe` файл, а также основные `.pak` и `.dll` библиотеки Electron).
## Node.js & Зависимости (Backend)
* Серверная часть использует CommonJS (equire). 
* **СТРОГИЙ ЗАПРЕТ:** Запрещено импортировать npm-пакеты, которые поставляются только как ES Modules (например, новые версии uuid, 
ode-fetch). При попытке это приведет к крашу ERR_REQUIRE_ESM.
* Вместо пакета uuid всегда использовать встроенную функцию crypto.randomUUID().

## WebSockets & Состояние гонки (Race Condition)
* При подключении к WebSocket на клиенте, статус online (например, в NetworkContext) должен устанавливаться **исключительно после** получения от сервера подтверждения авторизации (событие uth_success), а не сразу в событии ws.onopen. 
* Это гарантирует, что к моменту, когда React-компоненты начнут слать свои запросы (например, Clan Manager), сервер уже знает hwid клиента и не упадет с ошибкой базы данных SQLITE_MISUSE.
